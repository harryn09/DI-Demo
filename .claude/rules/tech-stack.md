# Tech Stack & Deployment

- **Hosting**: Microsoft **Azure App Service** (Azure Web Apps). Design and build with Azure deployment in mind from the start.
- **Database**: **Azure SQL Database** (managed) for relational dynamic content — e.g. service announcements, contact/support requests, FAQ content. Access it through a server-side layer only; never expose connection strings to the client. **Azure Table Storage** is used specifically for the signed-in user profile record (see auth below) — a simple key/value record that doesn't need a relational store; SQL remains the default for anything else.
- **Framework**: ASP.NET Core (Razor Pages + minimal API), the project root project (`DigitalIdentitySite.csproj`) hosts the existing static pages from `wwwroot/` unchanged and adds server-side auth/API endpoints. This is the natural fit for Azure App Service + Azure SQL and common in NZ government environments.
- **Authentication**: EntraID (Azure AD) via OpenID Connect, using `Microsoft.Identity.Web`. Config section `AzureAd` (Instance, TenantId, ClientId, ClientSecret, CallbackPath) is bound from configuration only — `ClientSecret` and `TableStorage:ConnectionString` are never in `appsettings.json`; they come from Azure App Service Application Settings (`AzureAd__ClientSecret`, `TableStorage__ConnectionString`) in production, or `dotnet user-secrets` locally. Sign-in/out endpoints: `/account/signin`, `/account/signout`; status endpoint `/api/me`; authenticated landing page `/account` (Razor Page, `[Authorize]`).
- **Configuration & secrets**: connection strings and secrets come from Azure App Service configuration / Azure Key Vault via environment variables — never hard-coded or committed. Use `appsettings.Development.json` (git-ignored) locally.
- **Data access**: Entity Framework Core with migrations for schema changes on Azure SQL; parameterised queries only. Azure Table Storage access goes through `Services/UserProfileStore.cs` only.
- Keep the public pages fast and cacheable — the site is primarily informational; the database supports it, it doesn't drive every request.
- **Local testing**: run `dotnet run` from the repo root to exercise auth, `/api/me`, and Table Storage — requires a real EntraID App Registration (redirect URI `https://localhost:<port>/signin-oidc`) and a storage connection string (real account or Azurite) configured via `dotnet user-secrets`. `dotnet-serve --directory c:\Projects\DemoSite\wwwroot --port 8080` still works for quick static-page/style checks but won't exercise auth (dotnet-serve is installed as a global tool; Node and Python are not available on this machine).
